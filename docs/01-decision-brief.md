# 参赛与 ICLR 双目标：侧重决策简报



## 1. 两个目标实际上在优化什么

| 维度 | 比赛 | ICLR 论文 |
|---|---|---|
| 核心产出 | 可批量运行的模型、标准 JSONL、技术报告与演示 | 清晰的研究问题、方法贡献、可信实验与可复现证据 |
| 直接评价 | 高光帧是否选对；同帧构图框 IoU；误报、漏报；运行有效性 | 新颖性、问题价值、强基线、消融、泛化、人类评价与论证完整性 |
| 数据条件 | 不提供训练集；测试集不可上传、人工标注或反向构造规则 | 训练与评测数据需可说明、可复核，并处理许可和发布边界 |
| 工程约束 | 固定 `[frame, x, y, w]` 输出、目标画幅、超时/越界/异常处理 | 工程只有在支撑研究结论时才构成贡献 |
| 公开边界 | 规则写明参赛作品须“未在其他比赛中获奖或公开发表” | 投稿、公开评审、预印本和代码发布可能产生时间与披露要求 |
| 主要失败方式 | 格式无效、推理不稳、帧召回不足、框不准、泛化差 | 与 STVG/视频摘要/自动重构图近邻重复，或提升无法证明来自核心方法 |

比赛不是单纯的“体育高光分类”：正式任务覆盖多类通用视频，同时联合要求**时间选择**和**逐帧构图**。这与现有 ICLR 探索的交集很大，但两者最终交付标准不同。

**兼容性前置问题：**赛题 PDF 没有定义“作品”和“公开发表”的范围。需要向组委会书面确认：ICLR 投稿、公开 OpenReview、arXiv、论文录用、代码/模型发布分别是否触发限制；同一底座但不同实验与交付物是否仍被视为同一作品。在确认前，不能假定参赛与投稿在规则上天然兼容。

## 2. 比赛内容摘要（可替代原 PDF）

目标是把原始长视频转换为结构化剪辑结果：既判断哪些帧应进入高光成片，又为每个入选帧给出适配目标横竖画幅的构图区域。测试内容不限于体育，还可能包括户外、演出、旅行/Vlog、课堂、会议和媒体素材，并包含抖动、遮挡、主体尺度变化、复杂背景及横竖屏混合等情况。

| 项目 | 规则摘要 |
|---|---|
| 输入 | 原始视频、测试样本索引和 `targetRatioWH`，常见目标画幅为 16:9 或 9:16。 |
| 输出 | 每个视频提交 JSONL；`predictions` 中每项为 `{"frame": 帧号, "bboxes": [x,y,w]}`。每帧只允许一个框，高度由目标画幅自动计算；无高光可提交空列表。 |
| 有效性 | 帧号、坐标、宽度和换算后的完整框均须合法且不越界；同一帧不应重复；格式错误、NaN、越界、超时或无法复现都可能导致无效。 |
| 核心指标 | 同一视频、同一帧直接计算预测框与真实构图框的 IoU。对每个视频，以 IoU 总和分别除以预测数和真实标注数得到精确率与召回率，再算 F1，最后对所有视频平均。错误帧、重复预测和误报会拉低分数，漏标会拉低召回。 |
| 数据 | 赛方不提供训练集，只提供样例、格式、评测脚本及各阶段不公开标注的测试集。可使用合规公开数据、自建数据和公开预训练模型，但须披露来源、清洗方式、许可证与用途。 |
| 测试集限制 | 不得上传到第三方模型服务、公开平台、仓库或社交媒体；不得传播、人工标注、人工修正预测、用于训练或反向构造规则。 |
| 模型与推理 | 允许公开预训练权重和开源视觉/视频/多模态模型；除非另行允许，禁止用商业闭源 API、在线人工服务或外部云端推理完成测试集推理。结果必须由提交的代码和模型自动生成并可复现。 |
| 主办方思路提示 | 可探索视频大模型、多模态建模、SFT、偏好优化/RL、SAM 类分割、候选高光生成、构图美学、跨帧平滑和推理加速。这些是思路引导，不是必须采用的技术路线。 |
| 阶段交付 | 初赛、复赛提交预测 JSONL；半决赛还需提交完整代码、模型、运行环境、推理脚本和技术报告；线下决赛另看复现、创新、演示与答辩。 |
| 公开与原创 | 作品必须原创，且规则写明“未在其他比赛中获奖或公开发表”；该表述与 ICLR/OpenReview/arXiv 的关系需向组委会确认。 |

## 3. 可以共用与必须分叉的工作

**可共用底座：**视频解码与长视频采样、多模态特征、高光候选生成、主体/语义重点定位、目标画幅构图、跨帧平滑、统一推理管线、数据许可记录，以及高光检测→重构图的两阶段基线。

**比赛分支：**严格复刻官方指标和 JSONL 校验；围绕排行榜做阈值、召回、框精度、速度、显存和异常视频优化；优先保证所有测试样本端到端成功。

**论文分支：**锁定一个可反驳的 thesis；全文核验最近邻工作；建立强基线、关键消融、跨域/跨运动验证和人类评价；解释“为什么有效”，而不只报告最终分数。

## 4. 三种侧重方式（不排序）

| 方案 | 时间与资源主线 | 比赛交付 | 论文交付 | 需要接受的取舍 |
|---|---|---|---|---|
| A. 比赛主导 | 以官方指标和提交稳定性排优先级 | 完整系统，尽快形成可迭代分数 | 从系统中提炼论文问题 | 容易得到工程增益，但论文贡献可能被视为模块组合 |
| B. 论文主导 | 先锁定 thesis、数据和决定性实验 | 将论文模型适配为参赛系统 | 围绕一个核心 claim 完成证据链 | 研究设计更集中，但可能牺牲对榜单有效的后处理和工程细节 |
| C. 共同主线、后期分叉 | 先建设共同底座，到预设 Gate 后拆成两个分支 | 独立维护稳健推理与榜单版本 | 独立维护可控实验与论文版本 | 复用率高，但要求明确版本边界，避免两个目标互相拖慢 |

## 5. 决策时需要填写的事实

1. **时间窗口**：比赛各阶段与 ICLR 官方 deadline；能否预留消融、人评和写作时间。
2. **规则兼容性**：组委会对 ICLR/OpenReview/arXiv/代码发布的书面解释，以及允许公开的最早时间。
3. **资源上限**：可用 GPU、存储、标注人力、队友分工，以及是否能同时维护系统版和研究版。
4. **早期信号**：官方评测是否能高频提交；现有 baseline 的有效分；时间选择与构图框哪个更影响分数。
5. **论文证据**：最近邻全文核验后，联合“选段 + 构图”是否仍有清晰缺口；adapted STVG 和两阶段 cascade 是否足够强。
6. **数据可行性**：能否获得合法的长视频→短成片对，自动恢复 crop trajectory；是否能建立多标注者或 acceptable-set 评测。
7. **个人目标权重**：比赛名次、ICLR 投稿质量、可复用产品能力三者的相对顺序，以及允许哪一个目标在本周期降级。

## 6. 决策前的最小证据包

- 一个完全跑通官方格式与本地评测的 baseline；
- 按模块拆分的误差统计：漏选帧、误选帧、构图 IoU、跨帧抖动、推理失败；
- 一个论文核心 claim，以及最可能推翻它的基线或消融；
- 训练数据、测试限制、开源发布和视频版权边界；
- 三种侧重方式各自的周级资源预算与最晚转向点。

在这些信息尚未填写前，任何“比赛优先”或“论文优先”的判断都主要是在表达偏好，而不是由证据支持的决策。
