# 时间监督与空间监督怎么合起来用

> 承接 [`04-data-sourcing.md`](04-data-sourcing.md) §0 的数据清单。本文回答：
> 这些数据集的监督信号结构上不兼容，怎么组装成一个联合模型的训练方案。
>
> `[F]` 已确认 · `[I]` 推断 · `[V]` 待核实。本文有多处 `[V]` 是**便宜且必须先做的检查**，不是搁置项。

---

## 1. 结构性问题：不只是「标注在两个集里」

朴素的看法是：Mr.HiSum 有时间标签、LIVE-YT VC 有空间标签，做个多任务、各自 mask 掉缺失的
loss 就行了。这个看法漏掉了三件事，每一件都会让你训出错的东西。

### 1.1 空间数据集里「每一帧都被选中」

LIVE-YT VC 和 RetargetVid 的任务是**把整段视频重构图**，不是「挑出好的部分再重构图」。
每一帧都有裁切框，没有任何帧被标为「不该进成片」。

**后果：如果你让时间头看到这些数据，它学到的是「永远选中」。**
这批数据必须从时间损失里完全 mask 掉——不是当正例，是当不存在。

更深一层：**空间数据集在结构上永远教不了选择行为。** 比赛指标要求的那个核心决策——
「真高光帧但构不出好框就该丢弃」（`u > F1/2` 规则）——在这两个数据集里没有任何对应物。
选择行为只能来自 Mr.HiSum 类的时间数据或自采的 S1 配对。别指望空间数据做它做不到的事。

### 1.2 两种「未标注」的语义完全不同

| 数据 | 未标注的含义 | 该怎么处理 |
|---|---|---|
| Mr.HiSum | 有**连续**重要性分数，低分不是「负例」而是「低分」 | 直接回归 / 排序，**不涉及 PU 问题** |
| 自采 S1 配对 | 未入选帧是真正的 unlabeled（短片有时长上限） | 需要 PU 损失 / 镜头内对比，见 `02-data-pipeline.md` §9 |
| LIVE-YT VC / RetargetVid | 没有时间标签这个维度 | 从时间损失中 mask |

**这条纠正了一个容易犯的错**：`02-data-pipeline.md` §9 的 PU 机制是为自采配对设计的，
Mr.HiSum 不需要它。把 PU 损失套到 Mr.HiSum 上是把连续信号退化成二分类，白扔信息。

### 1.3 90 个标注者，训练目标不是均值

LIVE-YT VC 每个视频有 90 名被试 `[V]`。如果你把它们平均成一个框去训，
**你恰好销毁了这个数据集最值钱的东西**。

单 GT 的 IoU 指标奖励预测均值。但论文的第二贡献（多参考 / 分歧）需要的是分布。
所以：**训练目标是标注者分布，不是均值框**——这正好接上 `03-repo-selection.md` 里
几何分支「输出 x 方向的分布 + 少量尺度，不是点估计」的设计。90 个被试的散布**就是**那个目标分布。

## 2. 造出联合标注集：本项目性价比最高的一步

两种监督分处两个集，那就去找或造出**同时有两种标签的帧**。

### 2.1 先查交集（成本：一小时）

Mr.HiSum 建在 YouTube-8M 上；LIVE-YT VC 建在 YouTube-UGC + LSVQ 上 `[V]`。
两者都是 YouTube 子集。**把两边的 video ID 列表求交。**

可能是空集。但只要非空，那些视频就是全项目唯一同时带
「逐帧重要性 + 逐帧裁切框」的数据——也就是 Control C / D 唯一的直接证据来源。
几十个视频都值。

### 2.2 如果交集为空，就自己造（成本：几天）

**关键观察：Mr.HiSum 的标签不是人标的，是抓来的。** 它的方法就是从 YouTube 抓
「最多重播」统计。那么同一套抓取逻辑可以**直接作用在 LIVE-YT VC 的视频列表上**。

```
LIVE-YT VC 的 1800 个 video ID
        │
        ├─► 已有：逐帧裁切框（90 名被试）
        │
        └─► 抓取 YouTube「最多重播」 ──► 逐帧重要性（5 万+ 观众聚合）
                        │
                        ▼
        同一批帧上，两种监督都有 —— 这个数据集目前不存在
```

零新增人工标注，只是把两个公开来源在同一批视频上对齐。

**必须先核实的三件事 `[V]`**（都很便宜）：

1. LIVE-YT VC 的视频在 YouTube 上**还在不在**，ID 是否可解析
2. 这些视频的**播放量是否够高到有「最多重播」数据**——这是最大的风险。
   YouTube-UGC 偏低播放量的 UGC，很可能大部分没有该统计
3. LIVE-YT VC 是否释出**逐被试的原始标注**，还是只给聚合/平滑版。
   VC++ 是「平滑版」这个事实暗示原始版存在，但要确认

第 2 条若失败，这条路就断了，需要换成：从 Mr.HiSum 里挑视频，反过来自己标少量裁切框。
第 3 条若失败，§1.3 的分布目标和 §3 的分歧信号全部失效——**这一条是最该先查的**。

## 3. 桥梁信号：用标注者分歧当 croppability

联合模型要学的核心是「选不选这一帧，取决于能不能构出好框」。
问题是：croppability 这个量在没有时间标签的数据上怎么定义？

**LIVE-YT VC 的 90 名被试直接给了答案。**

```
某帧上 90 个标注框的散布小  ⟹  构图唯一、明显  ⟹  croppability 高
某帧上 90 个标注框的散布大  ⟹  没有公认的取景  ⟹  croppability 低
```

这是一个**人类导出的、无需新标注的 croppability 标签**，而且它落在恰好没有时间标签的那批帧上。

它同时解决三件事：

- **Control C 需要一个可切断的 croppability 信号**才能做 blind 消融。这就是那个信号，
  而且它来自人类而非模型自身的置信度（用模型置信度做会有循环论证问题）
- **Control D 的反事实子集**（「内容强但不可构图」）可以直接用高分歧帧来筛，
  不必手工构造
- **DisagreeEdit / 多参考贡献**的原料就是这个分歧本身

⚠️ 但注意 `04-data-sourcing.md` §0 的警告：LIVE-YT VC++ 论文自己就在处理
「每帧只由一个人标注导致标签稀疏、时间不一致」的问题 `[V]`。
如果真是**每帧单人**（30–90 名被试分摊到不同帧，而非每帧都有 90 人），
那么「逐帧散布」根本算不出来，本节整条思路要改成跨帧/跨片段的统计量。

**这就是为什么读 LIVE-YT VC++ 全文排在写任何训练代码之前。**

## 4. 训练方案

对应 `03-repo-selection.md` 的三分支。每阶段标明用哪个集、哪个损失开着。

### 阶段 A · 时间分支预训练

| 项 | 内容 |
|---|---|
| 数据 | **Mr.HiSum**（31,892 视频 / 1,788 小时），可加 QVHighlights、SoccerNet |
| 监督 | 逐帧连续重要性分数 |
| 损失 | 回归 / 排序损失。**不要二分类，不要 PU** |
| 空间头 | 关闭（无标签） |
| 目的 | 时间选择能力的底座；也是「时间能力有多少来自灰色数据」消融的对照臂 |

### 阶段 B · 空间分支预训练

| 项 | 内容 |
|---|---|
| 数据 | **LIVE-YT VC**（1800 视频）训练 + dev |
| 监督 | 逐帧裁切框，条件于 `targetRatioWH` |
| 损失 | **对标注者分布做匹配，不是对均值框回归**（见 §1.3） |
| 时间头 | 关闭并 mask，**否则会学成「永远选中」**（见 §1.1） |
| 目的 | 构图能力底座；同时产出 §3 的分歧信号 |

### 阶段 C · 联合微调

| 项 | 内容 |
|---|---|
| 数据 | §2 造出的联合标注集 + 自采 S1 配对 |
| 监督 | 同帧上两种标签都有 |
| 损失 | 时间 + 空间，且允许两个头交互 |
| 目的 | **这是唯一能产生「联合性」证据的阶段**。Control C / D 都在这里做 |

**顺序不能换。** 阶段 C 的数据量最小（可能只有几十到几百个视频），
它只够做微调和消融，撑不起从头训练。

### 掩码规则汇总

| 数据来源 | 时间损失 | 空间损失 |
|---|---|---|
| Mr.HiSum / QVHighlights / SoccerNet | ✅ 连续回归 | ❌ mask |
| LIVE-YT VC | ❌ mask（**不是当正例**） | ✅ 分布匹配 |
| RetargetVid | ❌ mask | ❌ **完全不训练**，见 §5 |
| 自采 S1 配对 | ✅ PU / 镜头内对比 | ✅ 加权（用 `conf`） |
| 合成对 | ❌ mask | 仅用于抽取器评测与噪声消融 |

## 5. 划分纪律

`01-decision-brief.md` 里唯一标「不可妥协」的一条：论文永不依赖赛方测试集。
在具体数据集上落成如下。

| 数据集 | 角色 | 理由 |
|---|---|---|
| **RetargetVid**（200 视频，6 标注者） | **完全留出，只作最终空间测试集** | 200 个视频拿去训练是浪费；它规模小、多标注者、许可清晰，是最干净的独立评测集。**一次都不要在上面调参** |
| LIVE-YT VC | 训练 + dev | 规模够大，承担训练 |
| Mr.HiSum | 训练 + 时间维度 dev | 同上 |
| §2 联合标注集 | 阶段 C 微调 + Control C/D | 唯一的联合证据 |
| 赛方测试集 | **只进比赛提交**，论文一个字不写 | `[F]` 测试集不可上传、不可传播、不可人工标注 |

### 两套评测协议，同一个模型

| | 比赛 | 论文 |
|---|---|---|
| 真值 | 单 GT | 多参考 / acceptable-set |
| 指标 | IoU-F1（soft-Dice） | 覆盖率 / 分布匹配 / 人类偏好 |
| 操作点 | 调到最优 | **固定预测预算或给 PR 曲线**，禁止单点 F1 对比 |

第二列的「禁止单点 F1」来自简报 §03：仅调节预测数量就能显著改变 F1，
混进「方法增益」会被 hostile reviewer 一眼识破。

## 6. 依赖顺序

```
读 LIVE-YT VC++ 全文  ──┬─► 每帧是多人还是单人标注？   ──► 决定 §1.3 与 §3 是否成立
                        └─► 是否释出逐被试原始标注？   ──► 决定分歧信号能否算
            │
            ▼
求 Mr.HiSum × LIVE-YT VC 的 ID 交集 ──► 空集则走 §2.2 自造
            │
            ▼
抽样查「最多重播」在这批视频上的可得率 ──► <某阈值则 §2 整体改道
            │
            ▼
才开始写阶段 A / B 的训练代码
```

**前三步都是查证，不是编码，加起来不超过几天。** 而它们中任何一个的结果为负，
都会让后面的训练代码白写——`03-repo-selection.md` 里的架构选型也一样，
它假设的联合训练在 §2 失败时没有数据可训。
