# 数据从哪来，以及一对样本的具体处理

> 补 [`02-data-pipeline.md`](02-data-pipeline.md) 缺的一环：那份 spec 从「已经有一对长/短视频」开始讲，
> 但**候选对是怎么产生的**、**要花多少存储和时间**没有写。本文补这两块，并给出端到端的具体操作序列。
>
> 标注沿用：`[F]` 已确认 · `[I]` 推断 · `[V]` 待核实。
>
> **合规前置**：平台批量下载通常违反 ToS `[V]`，发布方式一律是「URL + 时间戳 + 标注」，
> 不再分发视频本体。详见 `02-data-pipeline.md` §11。本文只讲处理，不讨论任何绕开平台限制的手段。

## 0. 具体清单：公开数据集与平台

先回答「到底是 YouTube、TikTok 还是公开数据集」。答案是三者都有，但角色完全不同。
以下经 2026-09-04 联网核实，未读全文的地方标 `[V]`。

### A. 有空间监督（裁切框）的公开数据集 —— 只有两个，这就是你的 gap

| 数据集 | 规模 | 标注 | 来源 | 状态 |
|---|---|---|---|---|
| **LIVE-YT VC / VC++** | 1800 视频 | **90 名被试**，逐帧竖屏裁切区域 | YouTube-UGC + LSVQ | 号称最大的公开主观视频竖屏裁切库，2026-04 `[V]` |
| **RetargetVid** | 200 视频 | **6 名标注者**，IoU 评测 | — | ICIP 2021，GitHub 公开，附评测代码 |

**加起来两千个视频。这就是全世界公开的、带裁切框真值的视频数据的总量。**
你的数据 thesis 成立的原因就在这张表的短小——不是因为没人想要，是因为标注成本太高。

⚠️ **LIVE-YT VC++ 同时是资产和威胁，必须立刻读全文。**
它 2026-04 发表，用「帧内时间滤波」平滑主观标注，动机是
「虽然每个视频有 30 名被试，但**每一帧只由一个人标注**，导致标签稀疏且时间上不一致」`[V]`。
这个动机和你的 **DisagreeEdit / 多参考评测协议**（简报建议的第二贡献）几乎撞在一起。

但注意那句话的细节：**每帧只有单人标注**。所以「逐帧的多参考分歧」这个缺口可能仍然开着——
它有的是跨被试的视频级覆盖，不是逐帧的多标注。**这个区别决定你的第二贡献是否还活着，
必须读全文确认，不能靠摘要推断。**

### B. 只有时间监督的公开数据集 —— 多、免费、许可清晰

| 数据集 | 规模 | 监督信号 |
|---|---|---|
| **Mr.HiSum** | **31,892 视频 / 1,788 小时 / 3,509 类** | YouTube「最多重播」统计，每视频聚合 5 万+ 观众 |
| QVHighlights | — | moment retrieval + saliency（Moment-DETR 配套） |
| SoccerNet | — | 足球转播，action spotting + 集锦 |
| MovieNet / Condensed Movies | — | 正片 + 预告 / 影片片段 |
| TVSum / SumMe / YouTube Highlights | 50 / 25 / — | 经典视频摘要，极小 |

**Mr.HiSum 是这一档里唯一值得认真投入的。** 31,892 个视频的帧级重要性分数，
监督来自「最多重播」——**零标注成本的大规模参与度信号**，而且是从 5 万+ 真实观众行为聚合的。
NeurIPS 2023 Datasets & Benchmarks。它单独喂时间分支，回答
「时间能力有多少来自灰色数据」这个消融问题。

它没有任何空间监督。这正是为什么 A 和 B 两张表不能互相替代。

### C. 平台自采（S1）—— 关键认知：TikTok 单独毫无用处

这是最容易搞错的地方。**TikTok / Instagram Reels 只有短的那一半。**
你要的是「同一内容的长横版 + 短竖版」，只抓 TikTok 得到的是一堆没有源片的竖屏视频——
零监督，因为你不知道它是从哪里裁出来的。

配对只存在于**同一个创作者同时发布两种版本**的地方：

| 配对形态 | 说明 |
|---|---|
| **YouTube 长视频 + 同频道 YouTube Shorts** | 唯一大规模天然配对的地方。同一账号体系，元数据可用于索引分组 |
| YouTube 长视频 + 该创作者的 TikTok / Reels | 存在但跨平台，账号对应关系要人工建 |
| Twitch VOD + Twitch / YouTube clips | 直播场景，切片量大 |
| 机构官网 16:9 + 官方社交账号 9:16 | 新闻、联赛、活动主办方 |

**可发布性的唯一干净路径 `[V]`：YouTube 的 Creative Commons 授权筛选。**
YouTube 支持按 CC-BY 过滤，那是一个可再分发的真实子集。在策略 B 下版权是命门，
CC-BY + 同频道 Shorts 是唯一同时满足「可规模化」和「可发布」的 S1 路径。
非 CC 的部分照样能用于比赛（只要不再分发），但进不了论文的可发布数据集。

顺带：LIVE-YT VC 的源（YouTube-UGC、LSVQ）本身就是 CC 授权的 YouTube 子集 `[V]`，
Mr.HiSum / YouTube-8M / HowTo100M 一律以「视频 ID + 特征」分发而非视频本体——
这就是 `02-data-pipeline.md` §11 说的那个可发表先例。

### D. 没找到的东西（弱证据，不是证明）

针对「从长片 + 官方短片配对反推 crop trajectory」这个做法本身的检索**没有返回任何已发表工作**。
这支持 T1 thesis 仍然开着，但**这是搜索的缺席，不是不存在的证明** `[V]`——
正式的最近邻核验仍须按 harness 的要求做全文级排查。

## 1. 四个来源，按「什么时候用它」排

源文档按「能否拿到裁切轨迹」分梯队。但真正决定你先做哪个的是**成熟度**，不是监督强度。
所以这里换一个排法。

### 合成对 —— 今天就能开始，唯一 100% 可控

拿任意横屏视频，用自指定轨迹生成竖屏版。真值是你自己写的 crop 表达式，逐帧可解析。

源文档说它的产出是评测集不是训练集——对，别拿合成对训完去声称真实性能。
但它有**第三个用途文档没写**：主结果里那条「标签质量 vs 下游性能」曲线需要**受控噪声**，
而受控噪声只有合成对给得了。你可以精确地往标签里注入 5px / 20px / 50px 的轨迹误差，
再看下游掉多少。真实数据的噪声你只能估计，不能设定。

所以合成对承担三件事：抽取器精度评测、失败模式定位、**标签噪声消融的自变量**。

### 播客 / 访谈 / 讲座 —— 起步源，用来跑通管线和校准阈值

这是 S1 里最容易成功的一档，理由全是技术性的 `[I]`：

- **音轨是纯语音** → 指纹互相关峰值高而尖，时间对齐几乎必成
- **画面近乎静态** → NCC 模板匹配峰值高，空间配准的快速通道命中率高
- **竖屏切片通常就是满高裁切** → 落在 1-DoF 分支（`h = src_h, y = 0`，只搜 x），最便宜的那条路
- **一个长片对应大量切片** → 长片下载成本摊薄（见 §3）
- **变速少** → 斜率检验的丢弃率低

**但它不能当最终训练主料。** 比赛测试内容是户外、演出、旅行、体育、抖动、遮挡、
主体尺度变化——和固定机位对谈的域差极大。用它做 M0 / M1 的管线验证与阈值校准，
拿到 yield rate 和阈值 precision 之后再往难的域推。

**这是一个刻意的分工，不是偷懒**：先用容易的域证明抽取器能工作，再用难的域证明它能规模化。
两步的失败原因不会混在一起。

### 体育 / 新闻 / 机构账号 —— 主产能，但难度和风险都在这里

联赛官方、新闻机构、活动主办方通常同时维护 16:9 长内容和 9:16 社交切片。
域宽、量大，是真正的产能来源。代价：

- 快速运动 + 剪辑密集 → 时间对齐和空间配准都变难
- 调色、转场、字幕、贴纸多 → 丢弃率高
- 版权与可发布性风险最高 `[V]`，而这正是策略 B 下的命门

### 宽视野 + 虚拟机位（S2）—— 干净校准集，也是退路

Veo / Pixellot / Spiideo 类自动跟随、360° 原片 + 常规视场版、PTZ 讲座录制。
**空间监督是直接记录的，几乎没有配准噪声**——这让它成为标定 S1 抽取器误差上界的基准。

它的问题不是许可，是**可得性**：多数是商业系统，你得拿到系统侧的输出。
如果 S1 因版权不可发布，S2 是论文能站住的退路——所以别等到 S1 出问题才开始找。

## 2. 被跳过的一环：候选对是怎么产生的

源文档的 `pairing_rule` 假设你用元数据配对（标题前缀 + 发布时间窗）。
这个方向是反的。

**元数据配对不可靠**：切片标题经常重写，发布时间可能隔几周，描述里未必提原片。
你会同时有大量漏配和错配，而且错配要等到阶段 3 才暴露。

**指纹检索才是正解**：`短片音轨 → 在长片音轨库里检索`，一次操作同时给你
「配了哪个长片」和「对到第几帧」。配对和时间对齐本来就是同一个问题。

```
长片音轨库 ──► 建指纹索引（audfprint / Chromaprint）
                        │
短片音轨 ──────► 检索 ──┴──► (匹配到的 src_video_id, src_start_t, 峰值置信度)
                                  │
                                  └─► 无匹配 = 这个短片不是从库里任何长片剪的，直接丢
```

元数据在这里只剩一个作用：**缩小索引范围**。按创作者/账号聚类，让每次检索只在
那个创作者的几十个长片里做，而不是全库。这是性能优化，不是配对依据。

**实践后果**：`configs/sources_s1.yaml` 里的 `pairing_rule` 字段应该理解为「索引分组规则」，
不是「配对判据」。判据只有指纹峰值。

## 3. 关键操作决定：先音后视，两轮下载

这是本文最实的一条。源文档已经有「音频优先」的洞察，但没把它推到该有的结论。

### 问题

如果按「下载长片 → 下载短片 → 跑全流水线」的顺序，你会为大量**最终会被丢弃的对**
付全额视频下载和存储成本。而 yield rate 现在完全未知 `[V]`——可能是 60%，也可能是 5%。
按 5% 算，95% 的带宽和磁盘是白花的。

### 做法

**第一轮：只下音轨。**

```bash
# 只取音频流。1 小时长片 ≈ 60 MB（128kbps），对比 1080p 视频 ≈ 1.5 GB [I]
yt-dlp -f bestaudio -x --audio-format wav -o "audio/%(id)s.%(ext)s" <URL>
```

在纯音频上跑完：指纹建库 → 检索配对 → 互相关精修 → **斜率检验**。
所有「变速 / 速度斜坡」的对在这一步就被丢掉了，一帧视频都没下。

产出：一张表，每行是「短片 → 长片 + 起止时间 + 对齐置信度」，以及一个**早期 yield 下界**——
时间维度上有多少对能活下来。这个数字花几 GB 就能拿到，而不是几百 GB。

**第二轮：只对存活的对下视频，而且只下对应片段。**

因为时间对齐已经做完了，你知道每个短片对应长片的哪一段。一个 45s 的短片最多对应 45s 的源，
不需要整小时。

```bash
# 只取长片里对齐上的那一段
yt-dlp -f "bestvideo[height<=1080]" \
       --download-sections "*00:12:30-00:13:15" \
       -o "video/%(id)s_seg.%(ext)s" <URL>
```

然后才跑阶段 3 空间配准。

### 存储账（假设值，阶段 1 用实测替换）

| 量 | 假设 `[I]` |
|---|---|
| 竖屏切片时长 | 30–60 s → 900–1800 帧 @30fps |
| 长片音轨 | ~60 MB / 小时 |
| 长片 1080p 视频 | ~1.5 GB / 小时 |
| 一个长片产出的切片数 | 10–30 个 |

**举个例子**，目标 10 万帧带 crop 标签（这个目标值得你自己定，换算是线性的）：

- 10 万帧 ÷ 1350 帧/切片 ≈ **75 个可用切片**
- yield rate 10% ⟹ 需要 **~750 个候选切片**
- 750 ÷ 20 切片/长片 ≈ **~38 个长片**

朴素做法：38 × 1.5 GB = **~57 GB 视频**（其中 90% 会被丢弃）。

先音后视：
- 第一轮音轨 38 × 60 MB ≈ **2.3 GB**
- 第二轮只下存活片段 75 × 45s ≈ 56 分钟视频 ≈ **1.4 GB**

差一个数量级以上。yield rate 越低，差距越大——而 yield rate 低正是你最担心的情形。

### 组织单位是长片，不是对

一个长片摊到 10–30 个切片。所以缓存、去重、任务调度全部按 `src_video_id` 组织。
按「对」组织会把同一个长片下载 20 遍。

## 4. 一对样本的端到端处理

以下是单对的具体序列。每一步都标了失败时怎么办——**丢弃理由必须计数留档**，
因为「各丢弃理由占比」是指导你修哪里的唯一依据。

### 步骤 1 · 短片切镜头

```python
from scenedetect import detect, ContentDetector
shots = detect("short.mp4", ContentDetector())
```

一个短片通常是多个镜头拼的，每个镜头对应源里不同位置。**后面所有步骤的单位是镜头，不是短片。**

### 步骤 2 · 每个镜头在源音轨上定位

```bash
fpcalc -raw -length 0 src.wav     # Chromaprint 粗对齐
fpcalc -raw -length 0 shot.wav
```

粗对齐拿到候选位置后，用 chroma 特征做滑窗互相关精修到帧级。

- 峰值 < `xcorr_min_peak` (0.4) → 这个镜头在源里找不到 → **可能是插入的 b-roll**，标记丢弃
- 全部镜头都找不到 → 整对丢弃，配对本身是错的

### 步骤 3 · 斜率检验（变速检测）

对每个镜头拟合 `short_t → src_t`：

```
斜率 ≈ 1.0   → 正常
斜率 ≠ 1.0   → 变速或速度斜坡 → 整对丢弃
```

容差 `slope_tolerance: 0.02`。**这一步在纯音频上完成**，是第一轮下载的最后一关。
活下来的对才进入第二轮视频下载。

### 步骤 4 · 逐帧空间配准

对每个存活镜头的每一帧（或按 GT 粒度下采样，取决于未决事实 `[V]`）：

```python
import cv2
# 快速通道：满高假设，1-DoF，只搜 x
# 1920x1080 源 + 9:16 目标 → w = 607，h 锁死 1080，y = 0
res = cv2.matchTemplate(src_gray, short_resized_gray, cv2.TM_CCOEFF_NORMED)
_, peak, _, loc = cv2.minMaxLoc(res)
```

- `peak ≥ ncc_min_peak` (0.55) → 接受，`x = loc[0]`，`conf = peak`
- 失败 → 退到 3-DoF 粗到细搜 `(scale, x, y)`
- 再失败 → 这一帧丢弃

**从 NCC 起步，别一上来上特征匹配。** 尺度空间只有一维且窄，NCC 在重编码和轻度调色下够稳，
实现远简单于 SuperPoint + LightGlue。等失败案例攒够了再决定要不要升级
（升级时用 DISK / ALIKED，SuperPoint 权重非商用 `[V]`）。

若上了特征匹配：用 `cv2.estimateAffinePartial2D` 拟合相似变换，**把「旋转角 ≈ 0」当有效性检验**
——真裁切无旋转，估出旋转说明匹配错了。

### 步骤 5 · 一致性检查

- `scale > 1.0` → 短片比源更宽，物理上不可能 → 丢弃
- `|估计宽高比 - target| > 0.03` → 多半加了黑边 → 丢弃

### 步骤 6 · 轨迹平滑

对逐帧 `x(t)` 做鲁棒平滑（Kalman / Savitzky-Golay / 轨迹级 RANSAC）。

真实裁切轨迹是平滑的——人手 pan 或工具插值。每帧跳 200px 是估计失败，不是真实剪辑。

- 单帧残差 > `smooth_residual_max` (25) → 该帧标低置信
- 成片段残差超标 → 丢弃整个镜头

**平滑度过滤比逐帧阈值可靠得多**，因为它用上了「轨迹连续」这个强先验，而逐帧阈值没有。

### 步骤 7 · 内容过滤

- 文本检测（PaddleOCR / EAST）：文字/贴纸面积 > 15% → 丢弃
  **理由不是画面脏，是裁切位置可能在避让文字**——那是另一个目标函数，会污染标签
- 版式检测：分屏 / 画中画 → 非单窗裁切 → 丢弃

### 步骤 8 · 导出

按 `02-data-pipeline.md` §0 的契约落 JSON，同时导出可视化（源帧上画裁切框 + 短片对应帧并排）。

**可视化不是可选项**——阶段 1 的 50–100 对人工核对全靠它，而那次核对产出的
yield rate 和阈值 precision 是整条数据线是否成立的判据。

## 5. 现在的第一步

按依赖排，只有一件事完全不阻塞：

**`stage0_synth/`：合成对生成 + NCC 轨迹恢复 + 误差评测。**

它不需要任何真实数据、不需要任何未决答案、不触发任何合规问题，跑通就给你抽取器的第一个数字，
而这个数字是后面所有标签置信度的上界。同一套代码里的 NCC 恢复模块，
之后原样用在步骤 4 上——不是一次性脚本。

之后的顺序：

1. `stage0_synth/` —— 合成对 + 误差评测（无依赖）
2. 选 1–2 个播客/访谈源，跑**第一轮：只下音轨** —— 拿到时间维度的 yield 下界
3. 对存活的对跑第二轮，跑完阶段 3–6，人工核 50–100 对 —— 拿到真 yield rate 和阈值 precision
4. 用校准好的阈值往难的域（体育 / 新闻）推

## 附 · 本文相对源文档的三处补充

1. **配对不是元数据问题，是检索问题。** 指纹检索同时解决配对和时间对齐，
   `sources_s1.yaml` 的 `pairing_rule` 应降级为索引分组规则。
2. **先音后视两轮下载。** 源文档有「音频优先」的洞察但没推到下载策略上。
   在 yield rate 未知的前提下，这一条决定了数据线是几 GB 还是几百 GB 的事。
3. **合成对的第三个用途。** 除了评测和失败模式定位，它是「标签质量 vs 下游性能」
   曲线唯一的受控噪声来源——那是论文主结果。
